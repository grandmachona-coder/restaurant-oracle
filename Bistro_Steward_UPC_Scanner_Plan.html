1What this replaces

Today's inventory count is a four-step paper loop. It works, but every step adds latency, error, or cost:

1 · Print
Staff print a count sheet per area — a table of #, Item, Unit, Last Qty, New Count.
2 · Handwrite
They walk the area with a pen and write the new count in each row.
3 · Photograph
They snap a photo of the filled sheet on a phone.
4 · OCR (Gemini)
The scan op sends the image to Gemini 2.5 Flash Vision to read handwriting and match items — billed per scan, confidence-rated, and prone to misreads.
The pain: printing requires a printer and reprints when items change; handwriting + OCR introduces misreads (the model already returns "confidence":"low" when it can't read a number); every sheet costs Gemini tokens; and the whole loop is slow per area. The barcode path collapses steps 1–4 into a single point-and-scan for any packaged item.

What we keep: the OCR count-sheet path stays in place for items that have no barcode — fresh produce, prepped batches, bulk dry goods decanted into bins. This is the hybrid model you chose: scan what has a barcode, hand-count the rest exactly as today. Nothing about the existing prep workflow changes.

2Corrections to the original plan

The screenshot's "Key Decisions" carried four assumptions that would have caused real rework. Each is corrected below against what's actually in the repo.

DecisionOriginal (as planned)Corrected (grounded in repo)
Tech stack Next.js + Firebase ("existing") There is no Next.js. The app is a single large PWA page (firebase/public/app.html, ~568 KB of inline JS) served as static hosting, with all server logic in one Cloud Function (firebase/functions/index.js, ~6,000 lines) that dispatches on an operation field (op:'scan', op:'voice', …). The scanner ships as a module inside app.html and a new op:'upcLookup' — not a Next.js route.
Camera library jsQR (lightweight, zero deps) jsQR only decodes 2D QR codes — it cannot read 1D UPC/EAN barcodes at all. Retail UPC-A / EAN-13 are linear barcodes. The plan uses the browser-native BarcodeDetector API (free, on-device, already on most Android Chrome) with @zxing/library as the JavaScript fallback for iOS Safari and older browsers. Both run live off the phone's rear camera via getUserMedia.
Firestore 6 new focused collections, composite IDs Don't add a parallel inventory schema. The app already has its per-tenant collections under /tenants/{tenantId}/… plus audit_log, rate_limits, geminiUsage, and a Pub/Sub audit queue. The feature adds just a barcode field to existing ingredients and one shared upc_cache collection. Counts write back through the existing inventory path.
UPC API eandata.com only ($0.01–0.05/lookup) Free-first: query Open Food Facts (free, strong on grocery/food) first, fall back to a paid provider only on a miss, and cache every result in upc_cache so any given barcode is paid for at most once across all tenants. Reuses the existing geminiUsage-style cost-logging pattern.
Why the library correction matters most: had we built on jsQR, the camera would open, scan nothing off a grocery barcode, and the feature would appear "broken" with no obvious cause. Catching this before Phase 1 saves a full build-and-discard cycle.

3The hybrid count workflow

From the counter's point of view, each area now has two ways to log an item. The app picks the fast path automatically and falls back gracefully.

Packaged item
Point camera → barcode auto-detects → product name + size resolve from cache/API → confirm count with visual portion buttons or weight input → logged.
No barcode (prep/produce)
Unchanged: hand-count on the printed sheet, or type the count in-app. OCR sheet scan remains available.
Unknown barcode
Scan resolves to nothing → one-tap "link this barcode to an ingredient" → saved to that ingredient so the next scan is instant.

Portion capture

Per your earlier decision, two entry modes coexist after a successful scan: visual buttons for speed (¼ · ½ · ¾ · 1 · +1 steppers, matching the decimal quantities the app already stores) and a weight/quantity input for accuracy on partial cases or weighed goods. Both resolve to the same {qty, unit} shape the inventory model already uses.

4Revised architecture

The feature is three thin additions to surfaces that already exist — no new app, no new infrastructure.

Client — a scanner module inside app.html

  • A <video> + getUserMedia({video:{facingMode:'environment'}}) live preview.
  • A decode loop using BarcodeDetector when present, else @zxing/library (loaded from CDN, consistent with how the app loads other vendor scripts).
  • On decode: debounce duplicate reads, vibrate/beep on success, resolve the product, then show the portion-capture sheet.
  • Writes counts into the same in-memory inventory state and offline queue the app already uses.

Server — one new op in the dispatcher

if (operation === 'upcLookup') {
  // 1. validate barcode (UPC-A 12 / EAN-13 13 digits, checksum)
  // 2. read /upc_cache/{barcode} — return immediately on hit
  // 3. miss → Open Food Facts (free) → paid provider fallback
  // 4. write-through to /upc_cache, log cost like logGeminiUsage()
  // 5. enforce the same per-tenant rate limit + audit emit as scan/voice
}

It mirrors the existing scan and voice handlers exactly: same rateCheck, same writeAuditLog, same cost-logging discipline, same {data, error, _rateLimit} response envelope.

Data — minimal, reuses what's there

  • Add an optional barcode (string) to each ingredient record — the link between a physical product and a known ingredient.
  • One shared upc_cache collection keyed by barcode: product name, brand, size, source, fetchedAt. Shared across tenants because a Coca-Cola UPC is the same everywhere — this is what makes paid lookups one-time.
  • Counts continue to write through the existing inventory write path and the audit log; no new count collection.

6UPC lookup & cost control

The lookup is designed so the paid API is the exception, not the rule:

1 · Cache
Read upc_cache. Hit = free, instant, no external call. Over time this serves the large majority of scans.
2 · Open Food Facts
Free API, excellent food/grocery coverage. On hit, write-through to cache.
3 · Paid fallback
Only on a miss. eandata / UPCitemdb. Result cached so it's never paid for twice.
4 · Manual link
Total miss → user names it once; that mapping lives on the ingredient and seeds the cache.
Spend visibility: every paid lookup logs through the same cost-rollup the app uses for Gemini (tenant_costs_daily), so UPC API spend shows up in the operator console alongside AI cost — no blind spend.

7The camera scanner, in plain terms

You asked for "something that works from a user's camera on their phone." Here's what that means concretely and why this choice:

  • It uses the phone's own camera, in the browser — no app install. Bistro Steward is already a PWA, so staff just open it and tap "Scan."
  • Two engines, one experience. Modern Android Chrome has a built-in barcode reader (BarcodeDetector) that's fast and free. iPhones/Safari and older phones don't, so we bundle a proven JavaScript reader (@zxing/library) that does the same job. The staff member never sees the difference.
  • It reads grocery barcodes (UPC-A, EAN-13, and the rest), which is exactly what's printed on packaged kitchen goods — and precisely what the originally-planned jsQR could not do.
  • Permission & privacy: the browser asks for camera access the first time; we add a plain-language note about why, and the camera stream never leaves the device — only the decoded number (e.g. 049000050103) goes to the lookup.

10Open risks & decisions to confirm

Risk / questionDetail & mitigation
Food-service pack codesRestaurant suppliers (Sysco, US Foods) often use case-level GTIN-14 or internal SKUs, not retail UPCs — and those won't be in Open Food Facts. Mitigation: the manual-link flow turns any unrecognized code into a saved mapping after the first scan, so the system learns your specific supply over time.
iOS performanceZXing-in-JS is heavier than the native detector. Mitigation: lazy-load the bundle only when the scanner opens; validate frame rate on a real older iPhone in P2's exit gate.
Open Food Facts coverageGreat on consumer grocery, thinner on bulk/industrial. Mitigation: paid fallback + cache means a miss is paid once, then free forever after.
Paid provider choiceYou deferred eandata vs UPCitemdb to me. Recommendation: keep the provider behind a single config value so it can be swapped without code changes; pick after measuring real miss-rate during the LaChona pilot, when we'll know which codes actually fall through.
Net effect: packaged-goods counting goes from print → handwrite → photo → OCR down to point → scan → confirm, with no printer, no handwriting misreads, and near-zero per-scan cost after the cache warms — while prepped items keep working exactly as they do today.

Key distinction: brand and supplier are two independent axes for packaged goods. The brand is the product identity and carries the barcode (General Mills cereal — the UPC identifies the branded product). The supplier is where you bought it (Costco) and determines the price you actually paid. The same brand can be bought from several suppliers at different prices, so cost lives at the intersection of brand × supplier × date. For produce (strawberries, corn, steak) the two axes collapse: there's no barcode and the supplier is the brand. The model below handles both with one code path.

3 · Data model

CHANGE Ingredient gains a brands[] array; pricing is keyed by brand × supplier

Two structures, because the two axes are independent:

// AXIS 1 — Brand (product identity; carries the barcode). A sub-category of the // ingredient ONLY. Lives on the ingredient; recipes reference it by choice. ing.brands = [ { brandId, // stable id name, // "General Mills Cheerios 18oz" (for produce: the supplier name) barcode|null, // UPC/EAN identifies the BRANDED PRODUCT; null for produce packSize, packUnit, // e.g. 18 / "oz" -> normalizes to recipe unit cost isProduce, // true -> brand == supplier, no barcode isDefault // checkbox: default brand for EVERY recipe using this ingredient }, ... ] // Exactly one brand per ingredient may have isDefault:true (setting one clears the rest). // AXIS 2 — Supplier × brand pricing. Reuses the EXISTING priceHistory array, // just adds brandId alongside the vendorId it already stores. ing.priceHistory = [ { date, price, vendorId, brandId, packSize } // "GM cereal cost $4.20/box at Costco on 6/1" ] // ing.barcode + ing.cost stay as legacy/fallback (back-compat, lazy migration)
  • Packaged goods: each brand is one entry in brands[] with its barcode. Scanning any brand's UPC resolves to the ingredient and the specific brand. The same brand can appear in priceHistory against multiple vendorIds at different prices — that's the Costco-vs-Sysco distinction.
  • Fresh produce: brand entries have barcode:null and isProduce:true; here brand and supplier are one and the same, so each "brand" maps 1:1 to a vendorId. One code path, no separate produce system.
  • Back-compat: existing single barcode/cost stay; a lazy migration folds them into brands[0] (flagged isDefault) + a seed priceHistory row on first edit. Non-destructive, mirrors UPC Phase 1.

CHANGE Recipe lines can pick a brand

Recipe ingredient lines (rec.ings = [{ingId, qty, unit}]) gain one optional field:

rec.ings = [ { ingId, qty, unit, brandId|null } ] // brandId set -> this recipe uses that specific brand (per-line override) // brandId null -> falls back to the ingredient's isDefault brand

This is the resolution order the cost engine uses, most specific first:

  1. Recipe-line brandId — the brand explicitly chosen while building the recipe.
  2. Ingredient's isDefault brand — the checkbox-flagged default for all recipes.
  3. Legacy ing.cost — pre-migration fallback.

So the checkbox sets the house default everywhere at once; the recipe builder's brand picker overrides it for a single dish without touching others.

4 · Best-guess ingredient matching

Reuse the exact technique already in the count-sheet OCR: the scan op passes ALL KNOWN INGREDIENTS into the Gemini prompt and asks it to return the closest exact name. For receipts:

  1. Server (Gemini) returns, per line, a description + a suggested matchName chosen from the tenant's ingredient list + a confidence.
  2. Client resolves matchName → matchIngId; a lightweight token/Levenshtein fallback re-ranks when confidence is low.
  3. Barcode short-circuit: a printed UPC identifies the brand. If it maps to an existing brand.barcode, both the ingredient and the brand are matched exactly (confidence = high), skipping fuzzy matching. If it's a new barcode, it resolves via the UPC cascade and becomes a candidate new brand on the chosen ingredient.
  4. The dropdown in the dashboard is pre-selected to the best guess (ingredient + brand); the user confirms or overrides. The receipt's vendorId supplies the supplier automatically.

5 · Vendor-level recipe costing

Today calcLineIngCost uses one ing.cost. Because cost lives at brand × supplier, there are now two knobs — but we keep the single-number path working untouched:

  • Per line, the brand is resolved by the order in §3 (recipe-line brandId → ingredient isDefault brand → legacy). Cost = that brand's most recent priceHistory price, normalized to the recipe unit via packSize.
  • Add calcRecipeCost(rec, {vendorId, brandPref}) — an optional overlay. For each line ingredient it picks the price from the matching priceHistory row, filtered by supplier (vendorId) and/or brand. Already half-built: getBestVendorForIng groups history by vendor — we extend it to group by brand too.
  • Assigning a receipt line writes a priceHistory entry {date, price, vendorId, brandId} — a superset of the shape the function already reads — so both supplier and brand costing sharpen automatically as receipts come in.
  • Margin tab gains two optional selectors: "cost as if bought from [supplier ▾]" and "using [brand ▾]", so you can compare a recipe's margin across suppliers and across brand choices (e.g. premium vs. store brand).

6 · Capture & the Receipts sub-dashboard

Capture (phone)

REUSE the UPC camera overlay (web getUserMedia — no Apple Vision/native OCR). A "Scan Receipt" mode takes a full photo (not a barcode decode) and sends it to op:'receiptScan', which stores the image in Cloud Storage and returns the parsed lines + imageRef; the client then creates a receipts doc with status:'unassigned'. Vendor can be picked at capture or later.

Triage (web only — Margin ▸ Receipts)

NEW sub-view listing receipts (vendor, date, total, #items, status). Open one → table of extracted items; each row has qty/unit/unit-cost + an ingredient search/dropdown pre-filled with the best guess and an inventory-location picker (area / sub-area). Web-only, gated to desktop width.

On "Apply" (per line or whole receipt), mirroring applyScanResults: upsert/attach the brand to the ingredient (carry barcode + pack), append a priceHistory entry pairing the receipt's vendorId (supplier) with the line's brandId + price, optionally bump inventory at the chosen location, mark the line applied, and flip receipt status toward done.

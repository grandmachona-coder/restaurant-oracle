Grand Agent Team — Proposal

A two-tier review crew for the live multi-tenant Firebase PWA at bistrosteward.com. One orchestrator owns cross-branch contracts; eight branch agents own one functional surface each, and every branch fields a four-person sub-team (Functionality, Error-Handling, Security, Connectivity).

2The orchestrator

Orchestrator

Maître d' — cross-branch integrity

Owns everything that crosses two or more branches. Does not re-do branch work; instead, audits the seams.

JWT claim contract (tenantId / role / readOnly / impersonating) secureApi request/response shape Firestore namespace convention /tenants/{id}/... CORS allowlist regex Impersonation token lifecycle Audit-log schema across surfaces Scheduled-job → live-UI freshness Final consolidated report
Operating rules

How the team runs

Branches work in parallel against a frozen production snapshot. Sub-agents report up to their branch; branches report up to the orchestrator. Findings carry a severity (P0/P1/P2) and a branch tag so the orchestrator can route cross-branch defects to the right pair.

Read-only against prod (impersonation off) Parallel branch execution Severity-tagged findings Cross-branch defects routed by orchestrator

3The eight branches

Each branch owns one primary surface of the app and is accountable for intra-branch coherence — that the parts inside its surface fit together. Below: the branch's scope, the sub-team's focus, and the highest-value seams the branch reviews.

Branch 1 · Concierge

Identity & Tenancy

Auth, JWT claim issuance and verification, tenant resolution (slug + claim), RBAC matrix, impersonation read-only enforcement, approved-emails bootstrap.

F Sign-in, signup, claim mint, slug resolve, role grants
X Expired tokens, mismatched slugs, missing claims, suspended/cancelled tenants, replayed impersonation tokens
S Claim spoof attempts, readOnly bypass on writes, ownerEmail bootstrap window, JWT tampering, RBAC drift vs. PERMISSION_MATRIX
C Hand-off to Firestore rules, secureApi gating, operator console impersonation banner
Branch 2 · Line Cook

Kitchen Operations PWA (/app)

The ~9.6k-line app.html: recipes, ingredients, inventory, prep sheets, vendor orders, areas/categories, unit conversions, voice/scan entry points, Excel import/export.

F CRUD across 16 per-tenant collections, multi-shift shopping, prep math, Excel round-trip
X Offline → re-sync races, conflicting writes, unit-conversion edge cases, negative inventory
S Per-tenant scoping in every Firestore call, XSS in user-entered names/notes, file-upload validation

Branch 3 · Sommelier

5Cross-branch seams the orchestrator owns

Concierge ↔ Engineer

Claims minted by auth must match what Firestore rules expect. Drift here silently breaks RBAC.

Cashier ↔ Concierge

Subscription status (active/trial/past_due/cancelled) must drive the tenant status gate. A cancelled tenant must read-only immediately.

Sommelier ↔ Line Cook

OCR'd invoices update real ingredient prices. Wrong vendor mapping = wrong recipe cost = wrong margin.

Expediter ↔ Concierge

Impersonation tokens carry readOnly. Every write path must honor it; every audit entry must record the operator.

Host ↔ Cashier ↔ Concierge

Signup is a three-way handshake: Square sub + tenant doc + owner claim. Partial completion is the highest-risk failure mode.

Inspector ↔ all

Audit log is the cross-cutting source of truth. Every branch must emit, never mutate.

6Deliverables

Each branch returns: (1) a one-page summary keyed to F/X/S/C, (2) a defect list with severity + repro, (3) a seam diagram showing what it touches in neighboring branches. The orchestrator returns: (1) a cross-branch defect roll-up sorted by severity, (2) a contracts ledger (what each surface promises every other surface), (3) a prioritized punch list ready for engineering.

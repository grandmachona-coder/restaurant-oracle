💡
Core decision: single Firebase project, multi-tenant namespacing. Every customer gets a UUID tenantId in their Firebase Auth JWT custom claim, plus a human-readable tenantSlug. Firestore security rules enforce that they can only read their own path. Writes all go through secureApi() Cloud Function (Admin SDK bypasses rules).

🔒 Data isolation (Firestore rules)

match /tenants/{tenantId}/{col}/{doc=**} {
  allow read: if
    request.auth.token.tenantId == tenantId
    && request.auth.token.approved == true;
  allow write: if false; // Cloud Function only
}

Each customer's data is physically in the same Firebase project but logically isolated. Zero cross-tenant leakage possible with these rules. Hijack prevention (H-1 guard) also validates URL slug matches JWT slug.

⚡ Real-time sync: already solved

Firestore onSnapshot listeners are the core of Bistro Steward. The iPad in the kitchen and the laptop at the bar both subscribe to the same tenant namespace.

A change appears on every device in 100–300ms.

No additional architecture needed. This is the existing system, just namespaced per tenant.

Hosting strategy

Path-based tenancy

We had to pivot from wildcard subdomains after Firebase Hosting's 20-custom-domain cap was discovered. Path-based tenancy is the pattern Notion, Linear, and GitHub use.

Tier Customer URL How it works Cost Setup
Standard bistrosteward.com
/user/luigi		 Single Firebase Hosting site. SPA rewrite sends all paths to index.html. Client parses slug from URL with regex. $0 Provisioning Agent in 5 seconds
Premium upsell kitchen.
luigisbistro.com		 Customer adds CNAME pointing to Firebase. Firebase Hosting custom domain + auto Let's Encrypt SSL. Only works up to ~15 premium customers before we migrate to Cloud Run + Load Balancer. +$20/mo 1 email, Provisioning Agent, 5 min
White-label Fully branded domain + custom login Tenant-specific manifest + branding, tenant-scoped /user/{slug} under their own domain. +$50/mo One-time setup (~30 min)
⚡
One deploy = all 10,000 customers updated. Firebase Hosting CDN distributes the same index.html globally. When you push a new version, every customer gets it within minutes. No per-customer deploy pipeline, no Kubernetes, no containers.
⚠️
When path-based hits its ceiling: Firebase Hosting serves all tenants off the same CDN origin. SEO per tenant is limited (search engines see one domain). If tenants want truly independent branding (white-label beyond a few dozen), we migrate to Cloud Run + Load Balancer — unblocks wildcard subdomains but adds ~$30/mo fixed cost and more DevOps. Not a Phase 2 concern.

Open questions

Trial period — yes or no?

Options: (a) paid from day 1, cleanest billing; (b) 14-day free trial, card required upfront; (c) 14-day free, no card — highest friction reduction but more tire-kickers. LaChona Wine Club has no trial — same pattern is simplest.

? Decide before tenant onboarding

Starter caps — enforce in code or honor system?

100-item cap on Starter either needs CF-level enforcement (block item #101 with upgrade prompt) or soft-enforcement (dashboard nag + email). Hard cap is more code but clearer to users.

? Decide before AI agents ship

AI usage metering

Should Pro include unlimited AI scans, or a monthly cap (e.g. 500)? Gemini pricing is low now but 10×/day × 30 days = 300. Hard cap prevents abuse; soft cap (email at 80%) is friendlier. No usage data yet.

? Nice-to-have before launch

Data export on cancellation

GDPR/CCPA-friendly default: one-click JSON/CSV export of all tenant data, 30-day data retention after cancellation. Can defer post-launch but listing publicly on pricing page builds trust.
